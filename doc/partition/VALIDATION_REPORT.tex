\begin{abstract}
This partitioner takes a synthesized design and a system topology, chooses which logic belongs on each FPGA, and writes \code{mapping.txt}. It tries to keep signals from crossing FPGA boundaries repeatedly before reaching a register, reduce communication, and keep every FPGA below its hard LUT limit. The user can give it more search attempts or allow uneven LUT use when that helps communication and paths. The backend is pinned to Mt-KaHyPar v1.6.2.

The evidence covers NVIDIA NVDLA, OpenTitan Earl Grey, a 3,072-core PicoRV32 mesh, and an AES farm, each on one through four J4 targets. The strongest observed improvements include reducing NVDLA's worst uncaptured path from three FPGA crossings to two, reducing OpenTitan's from four crossings to three in a two-FPGA run, and improving several mesh path and communication counts together. Other cases show compromises rather than universal improvement. More search sometimes found a better candidate and sometimes stopped improving.

The selected mappings have independent Vivado resource and boundary checks. A later mapping-format repair also checked all sixteen maps against the exact synthesized hierarchy, without changing functional ownership. These are source-netlist results. They do not establish placed-and-routed timing, actual pin multiplexing, bitstreams or achieved DUT clock frequency.
\end{abstract}

\section{What a prototyping engineer can expect}

The normal input is a post-synthesis checkpoint, a topology JSON file, and optionally an FPGA count. If the count is omitted, the tool uses all FPGAs described by the topology. Each requested FPGA must receive useful nonconstant logic. Java, Python, Vivado 2025.1 and Mt-KaHyPar v1.6.2 must be available through the documented setup.

A typical four-FPGA job is:
\begin{Verbatim}[fontsize=\small]
.\partitioner.cmd --input "C:\designs\synth.dcp" `
  --system-topology "C:\systems\machine.json" `
  --target-part VP1902 --fpga-count 4 --iterations 3 `
  --output "C:\results\four_fpga_run"
\end{Verbatim}
The part can be omitted when the topology or its supported companion already identifies the targets. The output directory must be new or empty. On a POSIX host, use \code{./partitioner} with that host's paths. These are command examples; the placeholder paths are not experiments.

The main deliverable is \code{mapping.txt}. It names exact synthesized instances and their logical FPGA owners. It does not alter the netlist, insert communication hardware, add pipeline registers, or run the downstream regroup tool.

The optimization priorities are practical:
\begin{enumerate}
\item Respect hard resource limits and populate every requested FPGA.
\item Reduce the worst paths that cross FPGA boundaries before reaching a register.
\item Use the available source timing sample to identify important paths.
\item Reduce the remaining long-crossing endpoints and combinational transit logic.
\item Reduce communication while accepting a sensible amount of uneven LUT use.
\end{enumerate}
The exact acceptance order and guard limits are recorded in each run. A result can improve one quantity while worsening another; this report shows those cases explicitly.

\subsection{Capacity is a limit; balance is a preference}

The selected target part supplies the actual LUT capacity. The accepted mapping must fit the smaller of the requested explicit caps and 75\% of that part's LUT capacity. For VP1902, the queried capacity is 8,460,288 LUT elements, so the 75\% policy limit is 6,345,216 LUTs per FPGA. VU19P was separately checked at 4,085,760 elements, giving a 3,064,320 limit. Unsupported or conflicting part information is rejected rather than guessed.

The 75\% ceiling is the user's engineering rule. It leaves room for implementation, but it is not a promise that any design below 75\% will route. Wrapper, transport and debug logic are not included in these original-source subset measurements.

Balance asks how evenly the used LUTs are spread. For equal parts, 30\% imbalance means that the busiest FPGA uses 30\% more LUTs than the mean. It does not mean 30\% device utilization, or a 30-percentage-point difference between two devices. With two FPGAs using one million and three million LUTs, the mean is two million and the reported imbalance is 50\%. That can still be acceptable if both devices fit and the user permits that search envelope.

The preferred imbalance remains 20\%, but the new default search allows much more uneven candidates when they fit the devices. It derives the automatic search envelope from the selected parts' physical capacities rather than imposing a 30\% search envelope. For four equal parts its scalar envelope is 300\%; for three it is 200\%. These are permissive search bounds, not requested device utilizations, and useful logic on every FPGA is still mandatory. The hard Native LUT caps decide physical fit. This avoids chasing near-identical LUT counts simply for their own sake.

To request a tighter 70\% search envelope, use \path{--search-balance 0.70}. The separate raw-LUT guard is controlled by \path{--logical-balance}.

The preferred balance target remains soft. The historical experiments in this report used their recorded 28\%, 30\% or 70\% envelopes. Their results have not been rerun or relabeled as measurements of the new defaults.

\section{The numbers, in plain English}

\subsection{What counts as a snake path?}

Consider a signal that travels from FPGA A through combinational logic on FPGA B and then leaves B without being captured by a register. That is the transit behavior this tool tries to reduce. It matters even when the next destination is C: A--B--C has no return to an earlier FPGA, but B still adds an uncaptured boundary transit. A--B--A is another bad case. Counting only returns to an earlier FPGA would miss the first example.

The report uses three separate path measurements:
\begin{description}
\item[Worst uncaptured crossings:] The largest number of FPGA-boundary changes on a modeled path before the next register or terminal. Lower is better. A path staying on one FPGA has zero. A--B--C has two.
\item[Extra crossings at endpoints:] For each register input or modeled terminal, take its worst incoming uncaptured path, count crossings beyond the first, and add those excesses across endpoints. This shows how widespread multi-boundary paths are. It is an endpoint-based sum, not a count of every distinct path.
\item[Combinational transit cells:] The number of combinational primitives on an FPGA that can be reached from a cut input and can reach a cut output without a register in between. This counts cells, not paths. It shows how much logic participates in transit.
\end{description}
Older raw reports call these quantities \code{C} or \code{H}, \code{E}, and \code{V}. The tables below spell out their meaning. On J4, every selected pair is directly connected, so the worst minimum physical-link hop count equals the worst logical crossing count. That equality does not hold on every topology.

These measurements describe the supported structural dependency model. They do not prove that a path can be sensitized by real inputs, and they are not measured delays. Registers stop an uncaptured path; simply placing a register somewhere inside a large module does not make the whole module a register boundary.

\subsection{I/O cuts, hypergraph cuts and pins are different counts}

A net can have one driver and several destinations. The following example explains why a single number called ``cuts'' is ambiguous. If a driver on A sends one bit to both B and C, there is one crossing electrical net, two directed destination deliveries, and one participating bit at each of three FPGA boundaries. A has two outgoing deliveries but can share the same logical source bit. The eventual transport may route or multiplex these deliveries differently.

\begin{description}
\item[Crossing electrical nets:] Count each original nonconstant source net once when it crosses a partition boundary. Electrical aliases are joined before counting.
\item[Directed destination deliveries:] Count each crossing net once per remote destination FPGA. This is a useful logical communication measure, especially for fanout.
\item[Per-FPGA I/O cut bits:] The chart adds distinct outgoing and distinct incoming canonical data/functional-control net bits at that FPGA. Sending the same bit from A to both B and C counts once at A, once at B and once at C. Clock-only and reset-only nets are excluded from this chart and reported separately. Summing the chart values counts both ends of a point-to-point crossing.
\item[Cut hypergraph edges:] Count the abstract hyperedges whose vertices lie in more than one partition. A hyperedge is a solver representation, possibly after grouping hierarchy. Its cut objective is not automatically the same as the full electrical boundary census.
\item[Optimization transfers:] The solver/refiner's directed structural net-to-destination count. Some clock, reset and external-I/O scopes are excluded from this optimization view. Older raw reports call it \code{T}.
\end{description}
Neither crossing nets nor destination deliveries are physical pins, transport channels, TDM slots or a measured pin-multiplexing ratio. Those depend on the platform's links, routing, clocks, sharing rules and transport implementation. Ordinary clocks and reset-only distribution are reported separately from data and functional synchronous control. This separation matters because the platform may distribute clocks or resets outside its normal data pinmux.

The selected-map tables use independent Vivado boundary measurements where available. New run reports must state whether a number comes from the partitioner's source analysis or an independent Native Vivado boundary comparison. A Native LUT-resource check alone does not make the I/O counts independently verified.

\subsection{What does timing-aware mean here?}

The tool can export source setup paths and slack from Vivado and use them to weight communication and rank changes. Each selected multi-FPGA benchmark used a sample of 1,000 source setup paths. More critical sampled paths receive more attention. The tool also audits the worst modeled uncaptured crossings throughout its supported acyclic structural graph, beyond just the sampled timing paths.

This is timing guidance, not complete timing closure. The tool does not rerun a full platform timing analysis after each move. Many selected OpenTitan, NVDLA and mesh samples have zero modeled internal crossing cost; that does not mean zero delay, and those cases cannot demonstrate an improvement in sampled timing cost. AES does have nonzero sampled costs, with mixed results below. No measured inter-FPGA delay was supplied for the selected J4 studies, so this report makes no DUT-frequency claim.

\section{Does giving it more time produce a better partition?}

Yes, it can. It can also plateau. \code{--iterations} gives the frontend more feedback rounds using actual Vivado resource measurements. \code{--starts} gives the backend more starting assignments in each round. \code{--refine-passes} gives local path cleanup more passes. The default balanced effort is three rounds, three starts per round and three cleanup passes. Thorough effort uses five rounds, seven starts and six passes. Explicit flags override those presets.

A feedback round does more than repeat the same assignment: it can adjust proxy resource guidance after checking real Vivado LUT use. The tool keeps the best candidate it has accepted under its stated policy; rejected candidates do not replace it. More rounds therefore create more opportunities, but do not guarantee improvement in every measurement. The multithreaded backend also need not produce identical answers from a seed alone.

The revised frontend runs the requested multi-FPGA feedback rounds by default, even when it has already removed repeated uncaptured crossings. That leaves room to improve the remaining communication. Optional \code{--early-stop} restores the earlier stopping rule: stop when a fully analyzed, within-envelope candidate has at most one uncaptured crossing, no combinational transit cells and no extra topology-hop requirement. That rule does not establish that all I/O cuts are minimal. A one-FPGA request needs only its direct single assignment and no external partitioning backend.

\subsection{OpenTitan: improvement by attempt six, then no further accepted change}

Its worst uncaptured path improved from five crossings to four. Combinational transit cells fell from 6,842 to 5,469, and optimization transfers fell slightly from 3,481 to 3,476. The endpoint-excess sum became worse, which the higher-priority worst-path improvement allowed.

This longer run did not beat every earlier result. The earlier qualified four-FPGA map also had four worst crossings, with a smaller endpoint-excess sum of 27,667 and 3,529 optimization transfers. Its transit-cell count was 6,002. The newer run traded fewer transit cells and transfers for many more extra crossings at endpoints. Under the recorded selection order, the earlier result remained preferable. The original J4 package was therefore retained.

Two additional profiles raised the total to 23 feedback attempts and 276 starting solutions. A coarser grouping with a 15\% communication-growth allowance eventually selected a map at 48.48\% imbalance, 20,323 endpoint excess, 2,404 transit cells and 4,090 transfers. However, its worst path had five crossings rather than four. A separate three-round profile with a 20\% allowance retained four worst crossings, 27,768 endpoint excess, 7,833 transit cells and 3,679 transfers. Settings changed across these profiles, so they are alternatives, not a controlled proof that one switch caused an improvement. All three selected profile results received full-source boundary/category comparisons. Those proofs do not apply to every intermediate candidate.

The practical lesson is to allow longer search when the run is still improving, then inspect the actual tradeoffs. A wide imbalance envelope permits uneven maps; it does not force one. It also does not guarantee fewer I/O cuts or shorter paths.

\section{Reading a generated partition report}

Open \code{report.html} in the accepted output directory. It contains the selected mapping's measurements, figures, search history and validation limits. The three PNG files are \code{lut_balance.png}, \code{io_cut_balance.png} and \code{fpga_connectivity.png}. The corresponding numeric data and file identities are in \code{report_data.json} and \code{report_manifest.json}.

The accepted mapping is the selected candidate, not necessarily the last candidate attempted. Its report should be read in this order:
\begin{enumerate}
\item Check the acceptance status, selected FPGA count and target parts. Confirm that every requested FPGA has useful logic and passes its hard limit.
\item Read the LUT chart. The horizontal line is the mean; the deviation panel shows which devices are above or below it. A positive deviation is not a capacity violation unless the actual device limit is exceeded.
\item Read the I/O cut chart and its definition. Data/functional-control communication is separated from clock and reset-only distribution. A logical I/O cut count describes traffic to transport, not the final physical pinmux ratio.
\item Inspect the connectivity picture to find heavy communicating FPGA pairs. A dense logical relation does not itself choose a routed physical path through the topology.
\item Read worst uncaptured crossings, endpoint excess and transit cells together. A small total cut count can still hide one severe path.
\item If the search used several rounds, compare the accepted candidates and rejected attempts. A rejected attempt is not a new published mapping, and a missing measurement is not zero.
\end{enumerate}

The plots describe the selected mapping. The iteration history explains how the search reached it. Complete raw reports and manifests remain useful for developers, while the HTML report is the human-readable entry point. A separate independent full boundary check, when present, must be identified explicitly; normal frontend success is not a claim that the benchmark's complete Native census was rerun.

The LUT chart uses Native Vivado CLB LUT counts for the original mapped source subsets. Its second panel shows signed percent deviation from the arithmetic mean. The I/O chart uses the partitioner's canonical source-netlist analysis, with the data/control policy above; it is not automatically a new independent Native boundary comparison. Its second panel uses the same deviation formula. When every value is zero, deviation is defined as zero instead of dividing by zero.

The connectivity figure counts data/control net bits for each directed FPGA pair. The A-to-B-and-C example contributes one delivery to A--B and one to A--C, even though A's outgoing chart count is only one bit. Small systems include a connection drawing and a count matrix; larger systems use the matrix to keep the result readable. These are logical deliveries awaiting transport design, not selected physical routes.

The HTML uses restrained black-and-white styling. PNGs use the requested orange/black palette and a bundled regular display font, so the installed system font list does not change their layout. The drawing dependencies are pinned in \code{scripts/partition/requirements.txt}; font and rendering sources are included with the package.

\section{The mapping-file contract is a hard requirement}

The mapping consumer processes records in file order. It is therefore not enough to produce the right leaf-owner counts. The instance paths must exist in the exact synthesized design, and the move order must be valid.

A valid assignment line has exactly two whitespace-separated fields: the exact synthesized DUT instance path and a logical FPGA name such as \code{FPGA_1} or \code{FPGA_A}. Physical socket names belong to later board assignment. Generated files contain assignment lines only; the validator accepts blank lines and whole-line comments on input but rejects inline comments, duplicates, wildcards, quoted paths and one-field shortcuts.

The simplest two-partition example is:
\begin{Verbatim}[fontsize=\small]
hw_top/partition_b FPGA_2
hw_top FPGA_1
\end{Verbatim}
The first line extracts the child. The second moves the root's remaining logic to FPGA\_1. There is no implicit rule assigning unlisted logic to FPGA\_1: the explicit root line establishes that ownership.

Every mapped child must appear before every mapped ancestor. The root is last. Omit a child assignment when it has the same destination as its nearest mapped ancestor, because it adds no ownership information and can trigger downstream same-destination refactoring problems.

A nested return to the root FPGA is different and must remain:
\begin{Verbatim}[fontsize=\small]
hw_top/cluster_b/local_helper FPGA_1
hw_top/cluster_b/compute FPGA_3
hw_top/cluster_b FPGA_2
hw_top FPGA_1
\end{Verbatim}
Here the helper needs its own line: its nearest mapped ancestor, cluster\_b, belongs to FPGA\_2. Removing the helper just because it matches the distant root would assign it incorrectly. Sorting these records alphabetically or putting the root first would change their meaning.

Exact synthesized ancestry also matters. A slash can be part of an instance's local synthesized name. Splitting a string at every slash can invent a parent that does not exist. The revised writer follows actual EDIF parent objects and then checks how the serialized paths resolve. Generate indices, dots and selected branches must match the actual synthesized input. Explicit GND/VCC assignments are omitted by primitive type; constants and empty hierarchy cannot satisfy occupancy.

\subsection{What the 20 October audit found and fixed}

An exact-source audit reread all four source EDIFs and all sixteen delivered mappings. \section{Why these design choices have a research basis}

Mt-KaHyPar provides a mature multilevel hypergraph partitioning backend, including coarsening and local improvement \cite{mtpaper}. Version 1.6.2 supports direct target-graph mapping with a Steiner-tree objective \cite{mtdocs,steiner}. This lets communication cost depend on the declared system connections during optimization, rather than merely renaming partitions afterward. The same version does not provide multidimensional resource constraints, so the surrounding flow checks resource vectors and asks Vivado to verify actual LUT use \cite{mtformats}.

OpenROAD's TritonPart documentation describes using critical paths and slack during partitioning, then updating timing costs during refinement \cite{openroad}. The related paper explains why initially noncritical paths also matter \cite{tritonpaper}. Those ideas motivated timing-guided weights and path-based cleanup here. This implementation is narrower than TritonPart's full timing updates: it re-evaluates the exported source sample and uses its own conservative register-boundary graph. It does not claim to reproduce the complete TritonPart timing engine.

Research on multi-FPGA TDM explicitly links routing, communication pressure and multiplexing delay \cite{tdm2020,tdm2023}. This supports reporting heavily loaded pairs and data/control categories. It does not supply a universal conversion from total cuts to DUT clock. EasyPart also treats FPGA resources and system topology as part of partitioning \cite{easypart}. Public vendor material describes connectivity-aware, constraint-driven partitioning and timing-driven synthesis \cite{vendor}; it does not disclose enough detail to reproduce a proprietary tool's algorithm or claim equal results.

No cited research establishes one universal 3\%, 10\%, 20\% or 30\% cut/balance allowance. The default 10\% transfer-growth allowance is an explicit engineering choice reflecting the user's willingness to spend communication on severe path improvements. A different platform or design may justify another value. The hard device caps remain independent of those tradeoffs.

\subsection{How topology awareness was checked}

The code uses the selected target graph during backend initialization and local refinement. Path analysis also counts the minimum physical links needed between consecutive owners. Tests cover sparse connections, unreachable pairs, relay hops and the special case of a fully connected system. A relay hop is a lower bound based on declared connectivity; it is not a committed transport route or measured cable delay.

The sixteen selected large-design maps use J4, where selected FPGA pairs are directly connected. They therefore exercise the real topology input and device selection, but do not demonstrate a large sparse-machine speedup. Version 1.6.2 supports a target graph of up to 64 nodes in this direct mapping API, which permits 24/28-node experiments. That capability is not evidence that a completed final 24/28-FPGA result exists in this report.

Tests cover registers as path barriers, combinational transit, returns to an earlier FPGA, memory/DSP stage settings, synchronous versus asynchronous controls, unknown primitive behavior, cycles, topology hops, timing weights, fixed assignments, useful occupancy, hard caps and retained/rejected moves. Mapping tests cover exact source ancestry, record order, nested exceptions, redundant records, malformed records, constants, full ownership coverage and publication guards.

\section{What remains unproven}

The tool is a heuristic. It can fail to find an acceptable result, and it does not prove global optimality. A hard-cap promise means that accepted outputs must satisfy the measured cap; it does not mean that every request has a feasible answer.

The structural path audit is complete only on the supported acyclic dependency model. Unknown behavior or cycles must be reported as incomplete, rather than silently treated as safe. The source STA sample does not establish timing for every path. No selected experiment models measured board transport delay, performs downstream wrapping, produces final routed target utilization, or measures hardware DUT frequency.

The next useful evaluation would hold the source, topology, grouping, budgets and effort fixed, compare several deterministic seeds across balance envelopes, and retain the nondominated alternatives. A sparse 24/28-FPGA study should report pair/link bottlenecks, relay-hop bounds and actual target limits. A DUT-frequency claim then requires platform transport/TDM timing and constrained routed timing or hardware measurements.

\section{Technical definitions for developers}

The human-facing tables use full names. Raw developer files retain their stable field names for compatibility. This section gives an exact translation.

Let a modeled path visit primitives \(v_0,\ldots,v_m\), and let \(a(v)\) be a primitive's FPGA owner. Its boundary-crossing count is
\[
\text{crossings}(p)=\sum_{j=1}^{m}\mathbf{1}[a(v_{j-1})\ne a(v_j)].
\]
The raw field \code{C} is the largest such count over modeled paths. If \(h(x,y)\) is the shortest declared physical-link count between selected FPGAs, then the raw field \code{H} is
\[
\max_p\sum_{\substack{j=1\\a(v_{j-1})\ne a(v_j)}}^m h(a(v_{j-1}),a(v_j)).
\]
It is the worst minimum-link hop count, not a chosen transport route. J4's selected pairs have one-hop adjacency, so the two maxima coincide in these tables.

For each capture or terminal endpoint, take its largest incoming crossing count minus one, clamped at zero. Sum that over endpoints to obtain the raw \code{E} field, called \emph{extra crossings at endpoints} in this report. The raw \code{V} field counts the combinational transit primitives described earlier. The raw \code{T} field counts directed structural net-destination transfers in the optimizer's narrower scope.

The final path audit uses dynamic programming over all supported acyclic dependencies. Local move scoring uses a bounded witness set: at most 4,096 complete endpoint-maximal witnesses and a one-million primitive-ID aggregate default budget. That limit bounds refinement work; it is not the coverage limit of the final structural audit.

\subsection{Primitive behavior}

The selected model is \code{functional_synchronous_controls_v2_UNISIM_2025_1}. A sequential primitive captures incoming dependencies and launches an independent outgoing path. Functional synchronous reset/set and enabled internal stages participate according to their parameters. Asynchronous reset/preset or disabled stages do not become synchronous captures just because a pin name looks like a control.

Memory write/data/control captures are distinguished from asynchronous LUTRAM/SRL read-address dependencies. BRAM, URAM and DSP internal stage settings affect the model. Missing settings use the pinned UNISIM 2025.1 defaults. Invalid or unsupported settings cannot be assigned invented safe behavior. Unknown primitives and combinational cycles limit the claimed completeness. This is a conservative supported graph, not a full Boolean or pin-arc timing proof.

\subsection{Source timing weights}

For an exported path with source slack \(s_p\) and source requirement \(R_p\), the criticality is
\[
q_p=\max(0,1-s_p/R_p)^2.
\]
Normalize by the largest positive criticality in the exported sample, or by one when there is none. Eligible initial hyperedges then receive one plus a bounded rounded timing weight based on the largest matched normalized criticality. Matching uses ordered owner pairs and can conservatively affect parallel hyperedges; it is not exact pin-arc attribution.

The sampled path score combines criticality, topology hops, additional crossings and returns to an earlier FPGA. Without an explicit delay model, the retained-candidate ranking prioritizes worst minimum-link hops, worst logical crossings, sampled timing cost, endpoint excess and transit cells, followed by the remaining acceptance tiers. With a supplied extra delay per logical crossing, modeled sample slack subtracts that delay times the logical crossing count. This option does not discover omitted paths or measure real transport delay.

\subsection{Capacity and balance arithmetic}

For each target, the effective Native LUT cap is the minimum of its selected utilization fraction times its actual part capacity, any uniform explicit cap, any per-device explicit cap, and any topology cap. Unspecified terms are omitted, and the utilization fraction cannot exceed 75\%.

For equal parts, reported imbalance is
\[
\frac{\text{largest Native LUT count}}{\text{mean Native LUT count}}-1.
\]
For unlike parts, selection uses the analogous imbalance of capacity-normalized usage, while retaining raw imbalance separately. An experimental lower cap does not redefine a device's true capacity.

The preferred balance target, allowed search envelope and hard capacity are separate concepts. Cut/topology growth allowances remain anchored to the original reference through refinement; they do not grow on every accepted pass. Ranked acceptance can permit a lower-priority regression when a higher-priority measure improves. Componentwise acceptance forbids each listed regression. Hard capacity, useful occupancy and original budget checks remain separate gates.

In the reporting revision, the automatic estimated scalar search envelope is the larger of the preferred balance and \(\sum_i L_i/\min_i L_i-1\), using physical selected-part capacities. For equal devices this becomes the number of selected FPGAs minus one. The default raw logical-LUT guard is the larger of 0.5 and that equal-device bound. Explicit search/raw guard flags still tighten the search; Native physical caps remain hard. These new defaults broaden exploration, but do not by themselves establish a measured quality improvement over the historical runs.
